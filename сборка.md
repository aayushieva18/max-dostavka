# Журнал сборки — MAX mini app «Доставка»

> Заголовок и записи ниже до 2026-09-15 (переход на MAX) написаны, когда
> проект ещё назывался VK-версией — это история решений, часть из них с тех
> пор поменялась (см. запись «Полный переход с VK на MAX» ниже). Технический
> стек и текущее состояние — там же.

Статус: написана и проверена первая рабочая версия (Фазы 0–2, 3 и 5 из плана
в `AGENTS.md`; Фаза 4 — частично). Работает локально на этом компьютере,
до публикации ещё не готово.

## Решения
- Один агент на весь проект (не команда) — задача цельная, ведётся по фазам
  внутри одной роли.
- Стек и архитектура — см. раздел «Технические решения» в `AGENTS.md`.
- Экран покупателя и экран хозяйки (курьера) — одно приложение, разделение по
  VK id, а не два отдельных приложения.
- Публикация в VK, действия с VK-аккаунтом, установка программ без спроса —
  запрещены агенту, см. `задача.md`.

## 2026-09-14 — первая рабочая версия

Пользователь разрешила установить пакеты для разработки внутри папки проекта.
Собраны и проверены:

- `client/` — Vite + React + TypeScript + VKUI + vk-bridge. Экран покупателя
  (форма заказа, +/- по товарам, отправка заказа) и экран хозяйки (остатки,
  карта заказов, список заказов, кнопка «заказ выдал»). Переключение экрана —
  по VK id (`client/src/lib/config.ts` → `OWNER_VK_ID`, сейчас там заглушка,
  нужно вписать настоящий VK id хозяйки).
- `server/` — Node.js + Express + Prisma (SQLite) + Socket.IO. Товары,
  остатки, покупатели (с сохранением имени/адреса/телефона по VK id), заказы
  со статусами, живое положение курьера через сокеты. Оформление заказа
  проверяет остатки и не даёт заказать больше, чем есть.

**Важное техническое решение:** ставился Prisma — npm по умолчанию предложил
версию 8 (ещё не вышедшую стабильно, с другой, более сложной настройкой).
Осознанно закрепили версию 6.19.3 (последняя стабильная перед этим сломом
совместимости) — так проще и надёжнее для проекта, который не сопровождает
профессиональный программист.

**Проверено:** сервер и клиент собираются без ошибок (проверка типов и сборка
прошли), сценарий «заказ → списание остатка → нельзя заказать больше, чем
есть → хозяйка выдала → покупатель забрал» проверен запросами напрямую к
серверу — работает. Реальный экран в браузере пользователь может посмотреть
сама: открыть `http://localhost:5173` (при запущенном `npm run dev` в
`client/`) — в этой рабочей среде нет браузера, чтобы сделать скриншот самому.

**Не готово / известные ограничения:**
- Карта не покажет ничего, пока не вписан настоящий ключ 2ГИС
  (`client/src/lib/config.ts` → `DGIS_API_KEY`) — сейчас там заглушка с
  понятной надписью вместо карты.
- Адрес пока не переводится в точку на карте (геокодирование) — координаты
  заказа временно берутся по факту местоположения браузера покупателя.
  Настоящее геокодирование адреса и построение маршрута с реальным временем
  прибытия (Фаза 4 целиком) — делаем после того, как появится ключ 2ГИС,
  так как обе вещи используют один и тот же сервис 2ГИС.
- Добавление новых товаров хозяйкой пока делается напрямую в базе; форму
  «добавить товар» ещё не сделали — это мелкая, но нужная доработка.
- Сервер работает только локально на этом компьютере; куда выложить его,
  чтобы приложение работало не только у разработчика, — отдельный вопрос
  ближе к публикации (Фаза 7).

**Следующий шаг:** дождаться от пользователя ключа 2ГИС и её настоящего VK id,
вписать их в `client/src/lib/config.ts`, затем доделать геокодирование адреса
и маршрут с ETA (остаток Фазы 4), потом форму добавления товара, потом Фаза 6
(проверка на реальном примере вместе с пользователем).

## 2026-09-15 — смена карты на Яндекс, геокодирование и маршрут с ETA

Пользователь прислала свой VK id (`199675883`) и ключ — но назвала его ключом
от **Яндекс Карт**, хотя в плане был заложен 2ГИС. Уточнили напрямую: она
осознанно хочет Яндекс Карты, а не 2ГИС. Поменяли решение (см. `AGENTS.md`).

Сделано:
- Убрали `@2gis/mapgl`, подключили Яндекс Карты (JS API 2.1) через `<script>`
  с её ключом — карта, метки, оформление окрашены по статусу заказа.
- Настоящий VK id хозяйки и ключ Яндекс Карт вписаны в `client/src/lib/config.ts`.
- Геокодирование адреса заработало: при оформлении заказа адрес из формы сам
  переводится в точку на карте через `ymaps.geocode` — временное решение через
  геолокацию браузера убрали, это было заменой на время отсутствия ключа.
- Маршрут и время прибытия (Фаза 4) — на экране хозяйки строится маршрут
  (её положение → точки заказов по порядку в списке, без автоматической
  оптимизации по кратчайшему пути) через `ymaps.multiRouter.MultiRoute`,
  в списке заказов у неё показывается «в пути ~N мин» на каждую точку.
- Показ маршрута/ETA у самого покупателя (чтобы он видел время до своей
  двери) — ещё не сделан, это использует те же расчёты, что и у хозяйки,
  добавим отдельным шагом (нужно передавать посчитанный ETA от хозяйки к
  покупателям через сокет).

**Важная неопределённость, требует проверки самой пользователем:** ключ,
который она дала, точно открывает саму карту (проверено — грузится), но
отдельный публичный HTTP-геокодер Яндекса (`geocode-maps.yandex.ru`) на этот
ключ ответил «Invalid api key». Карта пользуется встроенным в JS API
геокодером (`ymaps.geocode`), который может быть завязан на ключ иначе и,
возможно, будет работать даже при таком ответе — но со стороны агента это
нельзя проверить без настоящего браузера (в этой рабочей среде браузера нет,
доступных инструментов вроде chromium-cli тоже нет). **Пользователю нужно
самой попробовать оформить тестовый заказ в браузере** и посмотреть, найдётся
ли адрес на карте. Если появится ошибка «не получилось найти адрес» даже на
правильном адресе — значит, в кабинете разработчика Яндекса у этого ключа
нужно отдельно включить геокодер (или тарифный план это ограничивает),
тогда разберёмся отдельно.

Проверено: типы и сборка (`npm run build`) в `client/` проходят без ошибок
после всех правок.

**Следующий шаг:** дождаться от пользователя результата тестового заказа в
браузере (нашёлся ли адрес на карте). Дальше — форма добавления товара у
хозяйки, показ ETA покупателю, потом Фаза 6 (полная проверка на реальном
примере) и Фаза 7 (подготовка к публикации, включая перенос сервера с

Пользователь подтвердила: поиск адреса не срабатывает («он не видит адреса»).

знать. Если снова не найдёт адрес — присылай пример текста один в один, как

**Следующий шаг:** попросить пользователя ввести именно тот же адрес ещё раз
(«чита мкр.хороший 14.43» или в свободной форме) и подтвердить, что точка

## 2026-09-15 — важный баг с данными: старые заказы показывали последний адрес

Пользователь заметила: в списке заказов у хозяйки все заказы показывают один
и тот же (последний использованный) адрес, хотя на карте точки — в разных
местах, все верно.

Причина — не в отображении, а в устройстве базы данных. Имя/адрес/телефон
покупателя хранились только в одном месте («карточка покупателя» по его VK
id), а каждый заказ просто ссылался на эту карточку. Когда один и тот же
покупатель оформлял новый заказ (например, с другим адресом — у себя дома и
на работе), карточка перезаписывалась, и ВСЕ его старые заказы в списке
начинали показывать этот новый адрес — хотя каждый заказ по-прежнему помнил
правильную ТОЧКУ на карте (у точки координаты хранятся отдельно, они не
трогались).

Исправлено: теперь у каждого заказа отдельно сохраняется имя/адрес/телефон

## 2026-09-17 — стоимость доставки за курьером + deep-link для общего бота в MAX

Пользователь задала два вопроса: (1) можно ли новому курьеру сделать платную
доставку, оставив её собственную бесплатной; (2) заранее предупредила про
важный момент — мини-апп будет ОДНА на всех курьеров, привязанная к одному
боту в MAX, и спросила, дорабатывать ли это сейчас или потом отдельно на
каждого курьера.

**Стоимость доставки:** у `Courier` новое поле `deliveryFee` (рубли, 0 —
бесплатно). Показывается покупателю в форме заказа и в статусе оформленного
заказа; сохраняется СНИМКОМ в самом заказе (`Order.deliveryFee`) — если
курьер потом поменяет цену, старые заказы не съедут задним числом. Курьер
меняет её на своём экране (карточка «Стоимость доставки»). Новый курьер
может сразу получить платную доставку через
`create-courier.ts <slug> "<Название>" <сумма>`.

**Deep-link для общего бота:** согласился с пользователем — лучше сделать
сейчас. Проблема была реальная: у бота в MAX в настройках — ОДНА ссылка на
мини-приложение, а не отдельная под каждого курьера; без доработки все
покупатели через один и тот же бот видели бы одного и того же (первого
вписанного) курьера. Решение — MAX поддерживает deep-link вида
`https://max.ru/ИмяБота?startapp=<slug>`, который передаёт `slug` в
`initDataUnsafe.start_param` мини-приложения. Приложение теперь сначала
смотрит на `start_param` (когда открыто изнутри настоящего MAX), и только
если его нет — на `?courier=` в обычном адресе браузера (`App.tsx`). Значит,
у каждого курьера будет своя `?startapp=` deep-ссылка на ОДНОГО общего бота,
а сам бот — один на всех.

**Попутно нашёл и исправил более серьёзный баг:** при тестировании платного
курьера оформление заказа стало иногда падать с ошибкой
`Transaction not found` — оказалось, стандартный 5-секундный лимit Prisma на
транзакцию (`prisma.$transaction`) впритык не хватает на её реальную длину
(несколько шагов подряд к облачной базе), особенно теперь, когда добавился
ещё один. Не связано с тем, через «pooler» подключение к Neon или напрямую —
проверил оба варианта, ловится одинаково; дело было именно в лимите
времени. Увеличил лимит транзакции до 15 секунд (`{ timeout: 15000 }`).
Заодно упростил и ускорил саму транзакцию: проверка остатка и списание
товара теперь один атомарный запрос на товар вместо двух (заодно чуть
безопаснее — не может быть, чтобы между проверкой и списанием кто-то другой
успел разобрать тот же товар). Это могло изредка ломать реальные заказы
пользователя и раньше (просто везло не попадать в лимит) — теперь надёжнее.

Также добавил `UserFacingError` — отдельный тип ошибки для сообщений,
которые специально показываем как есть ("Товара... не хватает"); любая
другая ошибка (например, от Prisma) теперь всегда прячется за общим
"Не удалось оформить заказ", не протекая техническими деталями наружу.

Проверено: платный тестовый курьер (создан и удалён после проверки) —
заказ с ценой 150 ₽ прошёл и сохранил цену; заказ у Арюны (бесплатно) —
прошёл с ценой 0. Реальные заказы и товары пользователя не пострадали
(проверено количество до/после — 23 заказа, ничего не потеряно; часть
были отмечены выданными/забранными самой пользователей параллельно, пока
шло тестирование — это её обычная работа с приложением, не имеет отношения
к тестам). Типы и сборка (`tsc`, `npm run build`) проходят без ошибок.
